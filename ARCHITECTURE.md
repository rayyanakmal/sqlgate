# SQLGate — Architecture

> Source of truth for HOW. SPEC.md is the contract; this document traces every design choice to its source.

## 1. High-level pipeline

```
question ("show me total revenue by month for 2025, top 5")
   │
   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ PROPOSER (pluggable, one of):                                        │
│   • StubProposer     — deterministic keyword → intent + slots (no key)│
│   • LLMProposer      — DeepSeek API → IntentProposal JSON            │
│   • FineTunedProposer— mlx-lm LoRA model (US-6, local)               │
│   Output: IntentProposal {intent, slots}  (the intermediate rep)     │
└─────────────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ THE GATE (deterministic — never changes with proposer):              │
│   stage 1  intent_validate  required slots present, types correct    │
│   stage 2  schema_validate  tables/columns exist, type-compatible    │
│   stage 3  safety_rules     SELECT-only; LIMIT on large tables       │
│   stage 4  sql_render       render pattern library template          │
│   stage 5  parser_check     sqlglot parse + AST (real SQL grammar)   │
│   stage 6  execution_oracle run against read-only SQLite, cap+timeout│
└─────────────────────────────────────────────────────────────────────┘
   │
   ▼
exact SQL query  OR  structured rejection {reason, detail, trace}
```

**The one-line story:** the LLM can only *propose meaning*. The gate renders, validates, and executes — so the final SQL is guaranteed to be schema-valid, safe, and runnable. False-accepts = 0 is a property of the design, not a test result.

## 3. Pipeline trace (one invocation)

Question: *"show me total revenue by month for 2025, top 5"*

1. **normalize** → lowercase, collapse whitespace (dedupe key)
2. **StubProposer.propose()** → `{intent: "aggregation", slots: {table: "orders", metric: "amount", aggregate: "sum", group_by: ["month"], filters: [{column:"year", op:"=", value:2025}], order_by: [{column:"revenue", dir:"desc"}], limit: 5}}`
3. **gate stage 1** intent_validate → slots present, aggregate ∈ {sum,avg,count,min,max}, limit numeric
4. **gate stage 2** schema_validate → orders.amount exists & numeric; orders.created_at exists (month extraction valid)
5. **gate stage 3** safety_rules → SELECT-only ✓; LIMIT present ✓
6. **gate stage 4** sql_render → `SELECT strftime('%Y-%m', created_at) AS month, SUM(amount) AS revenue FROM orders WHERE strftime('%Y', created_at) = '2025' GROUP BY month ORDER BY revenue DESC LIMIT 5`
7. **gate stage 5** parser_check → sqlglot parses; AST is SELECT; no unknown identifiers
8. **gate stage 6** execution_oracle → runs against `sample.db` (mode=ro), returns rows within cap
9. **accept** → SQL + result table + stage trace

## 4. Key components

### 4.1 IntentProposal (the intermediate representation)
From the internship's `IntentProposal` (family + slots) and Req2LTL's OnionL: a structured meaning that is neither the question nor the SQL. The proposer's entire output surface; the gate's entire input surface.

```json
{"intent": "aggregation", "slots": {...}}
```

### 4.2 The pattern library (data/patterns.json)
The SQL analog of the internship's template registry. Each pattern:
- `intent` (aggregation, filter, count, top_n, join...)
- `slot_spec` (which slots, types, required)
- `sql_template` (the deterministic render — no LLM touches this string)

| Pattern source | Why |
|---|---|
| Internship registry shape (signature + slot_spec + render) | Proven in production; the demo's whole point |
| Industry text-to-SQL validation guidance (dpriver 2026) | Parse → catalog bind → policy → record — our stages 2/3/5 |

### 4.3 The gate stages
Each stage is a pure function on (IntentProposal, schema) → (ok | rejection). Stages 1–5 are deterministic logic; stage 6 is the external oracle. New stages slot in without touching others (open/closed).

### 4.4 The execution oracle (oracle.py)
`sqlite3.connect("file:data/sample.db?mode=ro", uri=True)` — read-only at the *engine* level (writes are impossible, not just discouraged). Every query runs with: `PRAGMA query_only=ON`, row cap (e.g. 500), statement timeout. This is the external authority AC-1.2 requires.

### 4.5 Proposers
All implement one protocol. The gate treats them identically (AC-1.5):
- **StubProposer** — keyword tables + regex slot extraction. Zero cost, always runs, fully deterministic.
- **LLMProposer** — DeepSeek chat completion, system prompt carries schema + pattern manifest, output must be strict JSON; parsed defensively; garbage → PARSE_FAIL.
- **FineTunedProposer** (US-6) — same protocol; mlx-lm inference locally; results appear in demo via committed comparison table (AC-6.5).

## 5. Rejection taxonomy (fixed)

UNKNOWN_TABLE, UNKNOWN_COLUMN, TYPE_MISMATCH, UNSAFE_OPERATION, UNBOUNDED_QUERY, SLOT_MISSING, CROSS_INTENT_OVERRIDE, PARSE_FAIL.

Cross-intent override (from the internship's cross-family fix): a proposer proposal that contradicts the stub's owner-intent classification for the same question is blocked — the deterministic classifier wins on conflict.

## 6. Eval design (US-3)

Four layers, all committed + regenerable:
- **corpus/** — Spider e-commerce subset (real, public, cited)
- **golden/** — {question, gold_sql, expected_result_hash} (hash of executed result — execution-verified ground truth)
- **adversarial/** — must-reject negatives with expected reason (DROP/DELETE, unknown table/col, unbounded scans, cross-intent)
- **mutation/** — seeded paraphrases of golden questions

Metrics per layer: conversion, execution success, answer correctness, false-accepts (headline 0), reason accuracy, usable-draft %.

**Coverage lift** (AC-3.3): add a pattern → rerun → delta on corpus conversion. The internship's "template promotion is the lever" finding, made visible.


## 8. Test strategy

- Unit: gate stages (each stage's accept/reject paths), proposer parsing, oracle read-only enforcement
- Golden: eval-set regression runs with committed expected numbers
- UI: Streamlit runs against real sample.db; blind-design pass at P4
- Safety: adversarial suite MUST stay at false-accepts = 0 — a regression here is a release blocker

## 9. References & design decisions

| Decision | Pattern source | Why |
|---|---|---|
| LLM proposes / gate disposes | Hitachi Phase 3 hybrid verdict; Req2LTL; GM autoformalization | Safety + exactness by construction; limited-data friendly |
| IntentProposal IR | Internship IntentProposal; Req2LTL OnionL | Debug understanding separately from rendering |
| Pattern library = registry | Internship template registry | Deterministic render; coverage-lift metric |
| Execution oracle | ETM (arXiv 2407.07313); NL2Test value-consistency | Execution accuracy is the standard; external authority |
| Read-only engine + caps | dpriver 2026 production guidance; Streamlit spend controls | Safety at engine level, not policy |
| Reject-with-reason default | Internship verdict; Critical TechWorks; Ottawa study | Human review mandatory; auditable |
| Repair mode opt-in | Instructor/Guardrails retry loop | Show both philosophies, compare numbers |
| Stub default in demo | SPEC AC-1.5 | Demo always runs, $0, unlimited |
| Skip RAG layer | Vanna stale-example degradation | Schema-in-prompt suffices; RAG adds risk |
| Spider subset not full benchmark | BIRD 33GB / Spider 2.0 agentic scale | Demo-scale, honest scope |
